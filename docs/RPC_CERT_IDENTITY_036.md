# Priority 0.36 — pinned X.509 certificate-key possession for signed RPC

Date: 2026-10-13. **Experimental, opt-in additional authentication layer.**
**Production: NO-GO.**

## Threat model and implementation

Before 0.36, a valid per-peer HMAC secret authenticated the declared RPC sender.
There was no independent proof that the sender held the certificate key that
operators intended to assign to that peer. In 0.36, each pinned peer may
require BOTH a valid HMAC frame and a signature over the *exact request*
using the private key corresponding to a pre-pinned X.509 certificate.

The request signed by the private key includes the RPC `sender`, `recipient`,
UUID, issued time, TTL, and action. Domain separation is
`OCAF-RPC-CERT-POP-V1\0`. The signature is encoded in the HMAC-protected
frame. The gateway first verifies HMAC and recipient/TTL, then the
certificate proof, **before** replay admission, quota, tool discovery
or any external side effect. A failed proof cannot consume a replay nonce.
ECDSA (P-256) or RSA with SHA-256 are supported. Unpinned peers retain
the previously deployed HMAC-only protocol; a gratuitous certificate
proof to an unpinned peer is rejected.

Only operators can configure the mapping of **one pinned X.509 leaf
certificate fingerprint to one peer ID**. The runtime matches the
fingerprint to the DER of the configured PEM and verifies each request
using that certificate's public key. Certificate material is read
from an owner-protected file; public key and private key files must be
reviewed separately using `scripts/mtls_lifecycle.py`.

**CRITICAL LIMITATION:** this is an *application-layer proof of possession*,
NOT TLS exporter-based channel binding. In particular, the Zenoh query
API currently does not expose the authenticated TLS peer certificate
to `RpcGateway`; the gateway cannot prove that the TLS connection used
the *same* certificate. CA chain, EKU, SAN, certificate validity and
revocation must be validated independently by the operator/transport,
and a correctly pinned key is not itself proof that X.509 is currently
trusted. Do **not** report 0.36 as complete mTLS→RPC channel binding.
That production requirement remains explicitly open in the new roadmap.

## Coordinator: opt-in strict peer mapping

For each entry in the existing owner-only `OCAF_PEERS_FILE`, add:

```json
{
  "agent-a": {
    "key_b64": "<SECRET_32_BYTES_BASE64>",
    "allowed_tools": ["demo_echo"],
    "certificate_pem_path": "/etc/ocaf/pki/agent-a.pem",
    "certificate_sha256": "<LOWERCASE_SHA256_FINGERPRINT_OF_LEAF_DER>"
  }
}
```

No key or certificate is generated by this implementation. Private
keys and passwords must never be committed to git. Use
`python3 scripts/mtls_lifecycle.py` for the appropriate server/client
role, trusted CA and expected SAN before loading the peer.

For clients and workers executed by `ocaf-rpc-node`, set
`OCAF_RPC_CERT_KEY_FILE=/etc/ocaf/pki/agent-a.key` under the
service account. The key must be a real private file readable only
by the owner. The client automatically signs each new request. This
also applies to coordinator heartbeats sent from a demonstration node.

Both `certificate_pem_path` and `certificate_sha256` are required
together. Duplicate pinned leaf fingerprints across distinct peer
IDs are rejected at coordinator startup.

## Test plan

```bash
cargo test --locked --no-default-features --test rpc_cert_identity
cargo test --locked --no-default-features --test rpc_key_rotation
cargo test --locked --test rpc_security
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
```

Negative tests cover HMAC-only input to a pinned peer, wrong
certificate private key, tampered action, mismatched leaf fingerprint,
replay poisoning and gratuitous proofs on unpinned peers.

## Operations and unresolved requirements

- Do not send unencrypted RPC frames: Zenoh TLS policy remains mandatory.
- Do not use a certificate from a self-signed test issuer in production;
  runtime pinning alone is not PKI verification.
- Certificate rotation must update pin and private key material together.
  This stage does not hot-reload peers or support two certificate pins
  during overlap; changes require coordinated maintenance and service
  restart, after the stage-0.34 PKI preflight.
- Cryptographic channel binding **must** use the verified transport TLS
  identity / exporter; application payload claims cannot substitute.
- Tests do not demonstrate independently verified multi-host or
  production PKI authorization. This stage is not production certification.
