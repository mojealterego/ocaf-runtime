## Obowiązkowy mechanizm utrzymania tej Roadmapy

1. **Po zakończeniu KAŻDEGO etapu**: aktualizujemy jednocześnie `/ROADMAP.md`, `docs/ROADMAP_FULL_ECOSYSTEM_2026.md`, `docs/roadmap/canonical_v11_inventory.json`, wymagane produkty Code/NoCode, [dziennik etapów](roadmap/STAGE_CHANGELOG.md) i dowody CI. Wpis powinien wskazywać `stage_id`, status, kod/commit, zakończony URL workflow, wynik testów pozytywnych i negatywnych, artefakt SHA-256, realność backendu, konfigurację hostów, otwarte braki i `production_approved`.
2. Jeżeli przeprowadzono tylko część testów: status `PARTIAL/ACTIVE_TECHNICAL_OPEN`, nie `COMPLETE`; jeżeli brak realnego produktu: `NOT_IMPLEMENTED`; jeśli źródła są nieznane: `UNSPECIFIED`. Zewnętrzne audyty nie blokują **R&D**, ale nie wolno wymyślać podpisów ani wyników produkcyjnych.
3. **Odzyskane stare wymagania:** uzupełniamy pod **starymi** ID i opisujemy jako `RESTORED_EXISTING`; nie dodajemy ich jako nowych etapów. **Autentycznie nowe wymagania**: wyłącznie numer **kolejny po ostatnim etapie**, obecnie `1.95`, potem `1.96` itd. Inwentaryzacja i rejestr zmian są append-only; istniejących pozycji nie można skasować lub ukryć.
4. Workflow `roadmap-v11-builders.yml` oraz zachowany v10 kontrolują 195/64, zgodność plików i wymagane 10 odmian Agents Builder. Kod każdego etapu z osobna wymaga CI i dowodów wykonania, a nie samego zapisu w Roadmapie.

**Strumień wykonawczy:** P0 0.39–0.41 → P0 0.42 → P1 0.43–1.94 z zależnościami i śledzeniem. P0 można rozwijać równolegle, ale jego testów nie wolno zamykać bez prawdziwej topologii. Planowane crate z PDF **nie zastępują** istniejącego `Cargo.toml`: integracja ma być stopniowa i kompatybilna.
